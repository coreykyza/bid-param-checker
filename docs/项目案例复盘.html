01 / 项目背景

为什么做：一笔时间账、一笔质量账、一笔一致性账

设备或服务采购的招投标环节，评标要做一件很机械但很关键的事：把招标文件里的技术参数要求，和投标方提交的技术响应，逐条比对，判断每条是满足、不满足、还是说不清。

这不是开放式分析，而是一道有标准答案的判断题——规则明确、高频重复、判错代价高，天然适合产品化。

人工做，成本高在哪

1时间账

一份中等规模对照表，参数点通常几十到上百条。逐条读、找对应、判断，一条按 30 秒算，就是半小时到两小时的纯重复劳动，且每次采购都重来。

2质量账

最危险的不是判错，是漏了没发现。要求里提到某项能力、响应通篇没提——人眼扫过去容易默认"应该有吧"，实际是缺项，到验收阶段才暴露。

3一致性账

同一个参数，不同人结论不同：≥8GB 响应 16GB 是"满足"还是"超出需澄清"？点名对标型号时不懂硬件根本判不了。结果不可复核、不可交接。

为什么值得做：规则可枚举（能表达成规则 + 语义判断）、高频复用（每次采购都做）、错误成本高（漏判负偏离会导致验收扯皮甚至采购损失）。三点决定它不是 demo，是有真实交付价值的产品。

02 / 产品方案

从痛点到设计：六个决策的追溯链

一句话定义：上传招标/投标对照 Excel → 逐条判定每条参数的状态 → 输出带结论、可定位原文、带标红的核验报告。

产品定位不是"写一份漂亮报告"，而是"把需要人处理的地方挑出来"。这个定位决定了后面所有取舍。

核心设计：痛点 → 决策

用户痛点设计决策为什么这样解
逐条比对慢、量大判定权分层：规则本地判，语义歧义送模型把昂贵的 AI 调用留给真正需要理解力的地方
漏判看不出四态判定：缺项显式归入"待确认""没找到"必须暴露成结果，不能被默认为"满足"
统计对不上、不可复核输出契约固定：四态之和恒等于条目总数结构约束让统计天然自洽，不用事后修数字
结论对不上原文序号严格同步原文，不重新编号用户拿结论回 Excel 找原文，靠的就是原始序号
满屏结论看不出重点两档汇总 + 只列问题 + 标红招标列只让用户看"有没有问题、问题在哪"
型号参数不懂内置领域参数库，型号对标由库裁决把领域知识沉淀成产品能力，不靠模型临时发挥
产品判断最重的两条：① 把"不确定性"设计成一等公民——市面上很多工具把"没找到"当"满足"糊弄过去，那是拿用户验收风险换好看报告；② 克制——功能上能输出全部条目理由，但那会让真问题淹没在信息里。产品价值不在"给得多"，在"让用户一眼看到该看的"。

产品结构：四层，职责边界清晰

输入层    Excel 上传 → 识别 A 列（要求）/ B 列（响应）
   ↓
理解层    条目拆分（含多层编号）→ 结构识别（过滤分组标题）
   ↓
判定层    本地规则（数值/文本/型号库）→ 语义歧义送模型 → 异议复核
   ↓
输出层    四态结论 → 统计汇总 → 原文定位 → 标红导出

分层的好处：任何一层出问题可单独定位、单独替换——模型不行换模型，不影响拆分和导出；拆分规则要改，不用动判定逻辑。

典型场景：不看某份文件，看可复用的五类

场景类型典型表现结论判断依据
数值优于要求要求 ≥X，响应 >X正偏离数值方向裁决
数值低于要求要求 ≥X，响应 <X负偏离带具体数字说明差多少
单位不一致要求 min，响应"小时"换算后裁决基础单位知识库，换算到同一基准再比
型号性能对标"不低于 A 型号" vs B 型号库裁决比核数/线程/睿频，不比基础频率，功耗不参与
缺项 / 分组标题响应未提；或"硬件参数"大标题待确认/过滤不把标题当条目，不把缺项当满足
案例 A · 型号对标反直觉：点名"性能不低于 A 型号"时，B 型号基础频率反而更低，但它是更新代、核心翻倍。按"数字大的更好"会判成负偏离——错的。产品上把"型号对标"单独定义成场景，明确"比代际和核心规格、不比单一频率、功耗不参与"，并把参数库作为产品能力内置。这类判断靠提示词说不清，必须靠产品规则 + 数据。
案例 B · 单位不一致不能偷懒：要求"续航≥110min"，响应"16小时"。早期因单位不同直接判"待确认"，被用户当场否掉——本该工具做掉的换算甩给了人。现内置基础单位知识库（时间/存储/频率/功率/长度/重量/电量/网速等），换算到同一基准再比，结论写"响应16小时=960min，优于要求的110min"。边界守住：库里没有的单位（如 TFLOPS）仍不瞎判，保持待确认。该算的算，不该算的别装懂。

交付形态

单页 HTML + 本地代理，双击启动；命令行回归工具链，不依赖浏览器就能跑完整链路 + 自动验收；公网版本部署到云服务器，支持访问口令 + 开机自启，客户外网可用。

04 / 过程复盘

产品与交付视角的五个关键决策点

不按"写了什么代码"流水账，按五个决策点讲——每个都回答：遇到什么、怎么想、怎么解、沉淀了什么。

决策点 1 · 需求基线事件（产品第一课）
遇到：根据零散反馈迭代，用户发截图说"这里不对"就修，修了四轮，评价"质量很差"。
怎么想：不是修得不够细，是需求从来没被规格化。用户觉得"序号同步原文、汇总两档"是显然的，从没说过。
怎么解：拿到手写需求后逐条比对现有实现，判定"结构不匹配必须重做"，v2.0 重构。
沉淀：产品经理的价值不在接需求，在于把需求写成可验收的规格。
决策点 2 · 数据契约重做（结构性问题的识别）
遇到：模型只输出问题条目，满足项丢弃，靠"总数-问题数"反推——出现过"总数报10项却列28条问题"。
怎么想：连续修同类问题边际收益递减，不是某条规则不对，是模型输出形状和业务需要形状不一致。
怎么解：契约改成"每条必须给状态"，四态之和恒等于总数，统计自然自洽。
沉淀：连续三轮修同类问题时，停下来问——是不是底层契约错了？
决策点 3 · 性能瓶颈定位（交付的判断力）
遇到：全量核验 264 秒，太慢。
怎么想：先量瓶颈在哪。做工程优化（本地预判、并发、补漏）264s→141s，但瓶颈不在代码里，在模型。
怎么解：换模型 141s→秒级，漏返回 15→0；关掉思考模式再省一半时间。
沉淀：一直在给模型失误做兜底，本身就是"该换模型"的信号。
决策点 4 · 交付验证机制（从能跑到可信）
遇到：改完主流程后用户一点就崩——bug 藏在条件分支里，测试样本本地就判完了，走不到那行。
怎么想："我测过没问题"和"真的没问题"是两回事，单点测试覆盖不到分支。
怎么解：建命令行回归 + 5 条自动验收断言，每次改完跑全量，不靠肉眼。
沉淀：交付物必须可验证——把需求变成可执行断言，比"看起来对"可靠得多。
决策点 5 · 公网交付（交付经理的最后一公里）
遇到：本地跑通后，GitHub Pages 只能放静态文件，跑不了后端、藏不住 key——页面能开，一点核验就降级演示模式。
怎么想："本地能跑 ≠ 交付完成"。客户场景的约束（网络、系统、安全）必须在方案里解决，不能甩给用户。
怎么解：部署到云服务器；遇到 Windows Server、下载源慢、无鉴权裸奔，逐一解决——换国内镜像、加访问口令、注册开机自启。
沉淀：交付边界是"客户能用"。部署的每个约束都要当产品问题解决。

05 / 方法论

可迁移的五条
需求要写成可验收规格，不是口头描述
适用于任何产品与开发的协作，尤其是和 AI 协作
数据契约错了，改提示词没用
所有 LLM 应用：模型输出形状 ≠ 业务需要形状时，重设计输出格式
把"不确定性"设计成一等公民，不假装确定
判定类、审核类产品：诚实的不确定性优于看起来确定的错误
优化前先量瓶颈，别给错误的东西打补丁
性能与成本优化：发现一直在兜底时，问题可能在别处
交付边界是"客户能用"，本地能跑不算完
所有对外交付：部署约束要当产品问题闭环
