01 / 项目背景

一个规则明确、但极其耗人的活

设备采购评标时，需要把招标文件的技术参数要求（A 列）和投标方的技术响应（B 列）逐条比对。真实文件是 28 行、244 个参数点，每行 A 列还是一段含多层编号的长文本。

招标要求（A 列）投标响应（B 列）核验结论
1、处理器：≥6核12线程，主频≥2.3GHz，睿频≥3.8GHz，TDP≤35W（性能不低于 i5-10500T）1、处理器：i5-14500?
2、内存：≥8GB DDR42、内存：16GB DDR4?
3、积木种类≥90种，积木数量≥900块3、组件种类不少于40种，数量不少于323个?

人工做法的三个痛点

1慢且枯燥

244 个参数点，一条平均 30 秒就是 2 小时；熟练的人也要 40 分钟以上。

2容易看漏

最危险的不是判错，是跳过去了没发现。要求"支持声纹识别"，响应里压根没提，人眼一扫就默认有了。

3标准不统一

要求≥6自由度、响应9自由度，有人判满足有人判不一致；要求不低于 i5-10500T、响应 i5-14500，不懂硬件根本判不了。

为什么值得做：规则明确可自动化（不是开放式创作）、高频重复（每次采购都要做）、错了代价高（漏判负偏离会导致验收扯皮甚至采购损失）。

02 / 产品方案

四个设计决策撑起整个骨架

上传招标/投标对照 Excel → 逐条判定每条参数状态 → 输出带结论、明细、标红的核验报告。看似简单，但有四个决定成败的决策。

决策一 · 逐条四态判定，而不是"只报问题"

✗ 错误做法（v1.x 犯过）

只让模型输出"有问题的条目"，满足的不管。

后果：满足项被丢弃后，靠"总数 − 问题数"反推的满足数不可信。实际出过事故：模型报「共 10 项」，却列出 28 条问题。

✓ 正确做法

模型必须对每一条输出状态，四选一。核心约束：四个状态之和恒等于条目总数。

这条约束让所有统计天然自洽，不需要事后"修数字"。

状态含义示例
匹配响应满足要求（含等于阈值）要求≥8GB，响应8GB
正偏离响应明确优于要求要求≥8GB，响应16GB
负偏离响应低于 / 不满足要求要求≥90种，响应40种
待确认投标里找不到对应内容，或表述含糊要求声纹识别，响应未提及

决策二 · 序号严格同步招标原文

招标原文是多层编号的：

一、脑电波采集交互
1.采集方式：佩戴设备
2.实时采集信号
二、手势识别交互
1.采集方式：屏幕绘制

结论里必须原样输出 【1.】、【二、1】、【（3）】，不重新编号。

为什么这是关键：用户拿着结论回 Excel 找原文，靠的就是序号。如果我自己造"第1项、第2项"，用户根本对不上。多章节场景下四个章节都有"1."，重编号必然混乱。

决策三 · 汇总只有两档，明细只列问题

汇总：全部满足 / 部分满足，没有第三档。明细：只列负偏离和待确认，不列匹配和正偏离。

因为工具的定位是"找出需要人处理的地方"，不是"写一份完整报告"。用户扫一眼 C 列，只想知道：这行有没有问题、问题在哪。

部分满足｜共17项：负偏离6/待确认10/匹配0/正偏离1

负偏离：
  1、【2、】存储不低于16GB，支持SD卡。->仅4M flash/224K RAM，远低于16GB且未提SD卡
  2、【3、】主控器配备不小于4英寸触摸屏。->响应128*64LCD屏，远小于4英寸触摸屏

待确认：
  1、摄像头像素300w->投标参数中未找到对应内容，置信度0.5

决策四 · 标红只标招标列

最初做法：把 C 列结论整格标红 → 红色满屏，反而看不出重点。用户要看的是"招标要求里哪一条有问题"，不是"哪一行有问题"。

最终做法：只把 A 列中负偏离/待确认的那几段文字标红加粗，C 列不整格红。

这个决策带来一个硬技术难点：Excel 一个单元格内的局部文字变色，需要写富文本（rich text runs）。普通导出库只支持整格样式，做不到。解法见下一节。

最大的产品教训 · 需求必须写成可验收的规格

v1.x 阶段我是靠用户发截图反馈迭代的：说这里不对，我修一下，再等下一张。修了四轮，用户评价"质量很差"。

转折点是用户自己手写了一份需求文档，写清了：每个条目独立判定、统计口径、序号同步原文、汇总两档、明细只列问题、标红的是招标列。

拿到文档后我做的第一件事不是改代码，而是逐条比对现有实现，判定"结构不匹配，必须重做"。

产品经理的价值不在于提需求，而在于把需求写成可验收的规格。用户脑子里清楚"序号要同步原文"，但前四轮从没说过，因为觉得"这不是显然的吗"。恰恰是这些"显然的细节"，决定了工具能不能用。

03 / 实现路径

三个技术难点 + 三板斧提速

技术选型

层选择为什么
前端单页 HTML（1217 行，无框架）产品经理要能自己启动、自己改。不需要构建工具
后端Python 标准库 HTTP 服务（200 行）只做两件事：托管静态文件 + 转发 LLM 请求（藏住 key）
模型火山引擎 Ark · DeepSeek V4.1 Flash换模型是最大的性能杠杆（后面详述）
ExcelSheetJS（读）+ JSZip（后处理富文本）局部标红需要绕过库的限制
部署本地运行，双击 .command数据敏感（招投标文件），不出内网

难点一 · 单元格内局部文字标红

问题：SheetJS 只能读富文本、不能写（写进去得到空值）。Excel 的"一格内部分文字变色"需要 <is><r><rPr> 这样的富文本 XML。

// 正常导出 xlsx → 用 JSZip 打开 → 直接改 sheet XML
<c r="A15" s="4" t="inlineStr">
  <is>
    <r><rPr>...正常样式...</rPr><t>前面的文字</t></r>
    <r><rPr><color rgb="FFFF0000"/><b/></rPr><t>要标红的文字</t></r>
  </is>
</c>
踩的坑：读单元格文本时，部分原文件的 c.r 是原始 XML 字符串（<t>...&#10;...），直接当文本用会污染标红内容。必须优先取 c.v。

难点二 · 给条目找对「对应的投标内容」

这是整个项目最容易错、也最影响准确率的地方。场景：A 列第 3 条要求「积木种类≥90种」，B 列里哪一条是它的响应？

试过的方法为什么不行
按序号匹配多章节场景下 A 有 4 个"1."，B 也有 4 个，全对错了
按文本相似度长词分词放大数值差异，"≥8GB" vs "16GB" 相似度不足 0.5，找不到对应条目 → 数值判断根本没机会跑
按位置A/B 条目数经常不相等（B 可能合并或拆分），位置对不上

最终解法：序号 + 同序号出现次序

A 的第 1 个 "1."  →  B 的第 1 个 "1."
A 的第 2 个 "1."  →  B 的第 2 个 "1."

同时把文本相似度从「长词命中率」改成 2-gram 滑窗命中率做兜底。效果：不少于6自由度 vs 9自由度（颈部6+机身1+天线2） 从"匹配失败"变成"正确判正偏离"。

全场最重要的技术教训："找对应关系"比"做判断"更容易出错。找错对象时，后面所有数值比较、文本一致性判断全部建立在错误基础上，答案必然错，而且错得毫无征兆。

难点三 · 型号参数需要外部知识

问题：要求「≥6核12线程（性能不低于 i5-10500T）」，响应「i5-14500」。模型不知道这两颗 CPU 谁强，判成了"负偏离"。

解法：建本地型号参数库 —— 101 个内置型号（Intel 8~14 代、AMD、NVIDIA、树莓派），字段含核数/线程/频率/功耗/显存。

关键设计决策原因
型号之间只比核数/线程/睿频，不比基础频率i5-14500 基础频率 2.5，反而低于 i5-10500T 的 2.9，但它是 14 核。比基础频率会得出"14500 更差"的荒谬结论
点名"性能不低于 X 型号"时，功耗不参与i5-14500 是 65W，会撞上招标的"TDP≤35W"被判负偏离，但它性能远超。点名对标型号时用的是"性能档位"语义，不是散热约束
投标没给型号时判待确认不知道就是不知道，让人工去核，不能瞎判
结果：i5-14500 那条从「负偏离：低于 i5-10500T」变成「正偏离：核数 14vs6、线程数 20vs12、睿频 4.9vs4.3」。

工程配套 · 让 AI 能自证

这个项目有个特殊约束：我没有图形界面可以点，每次验证都要重启服务 + 开浏览器 + 等几分钟。所以做了套命令行工具链，不依赖浏览器就能跑完整链路。

验收脚本是关键：它把"需求文档"变成了可执行断言 ——

验收断言

验收2统计数字 == 明细行数

验收5"全部满足"行不出现明细
每次改完代码跑一遍，不靠肉眼判断"应该没问题"。

05 / 项目复盘

最有价值的部分：四条弯路

先看做对了什么

判定权分层：规则优先，模型兜底

不确定的规则（数值大小、型号性能、文本完全一致）全部放前端代码，只有"需要语义理解"的才交给模型。

结果：模型即使判错，也会被本地规则纠正。这解释了为什么换模型前后关键案例都判得对。

加了自动验收，不靠肉眼

5 条断言覆盖了最容易出错的统计一致性和格式同步。

v2.0 之后没再出现"统计不自洽"这类低级问题。

需求文档化后才动手

虽然是被"骂"出来的，但拿到手写需求后重做的效率，远高于之前四轮散点修补。

把踩坑原因写进代码注释

比如「这里要用 pre 不能用 rows」「型号对比不比基础频率」。

原因：项目大量依赖 AI 辅助编码，而 AI 每次对话都是失忆的。不写下来，下次同样会犯。

四条弯路

弯路一 · 给模型的错误打补丁，越打越歪（v1.0 → v1.4）
现象：用户说"这条判错了" → 加条规则 → 下次另一条又错 → 再加规则。四轮下来修了数值方向、二级序号、局部高亮、正偏离误报。

根本问题不是某条规则不对，是数据契约错了。v1.x 让模型"只报有问题的条目"，满足项被丢掉，前端靠"总数 − 问题数"反推满足数。这个设计从第一天就不可能自洽。
用户手写需求文档 → 逐条比对现有实现 → 判定"结构不匹配，必须重做" → v2.0 输出契约改成"每条都必须给状态"
弯路二 · 只跑单行就宣布"修好了"（v2.4 翻车）
v2.2 加进度提示时写了 rows.reduce((s,r) => s + r.items.filter(...))。但 rows 是原始行，没有 items 字段。用户一点核验就崩。

为什么没发现：这行在 if (jobs.length) 里面，只有"存在需要送 AI 的条目"才执行。我测试的样本本地就判完了，走不到这行。
改主流程后必须跑全量。另外异步主流程应默认包 try/finally 复位 UI —— 这次出错后按钮永久锁死，只能刷新页面，是二次伤害
弯路三 · 把工程优化当成了主要矛盾（v2.2）
花不少功夫做本地预判、并发池、补漏机制，264s → 141s，觉得挺满意。

真相：换个模型 141s → 6.6s，而且准确率还提升了（漏返回 15 → 0）。
优化之前先量瓶颈在哪。这次瓶颈根本不在我的代码里，在模型。不断给模型失误做兜底逻辑，本身就是"该换模型"的信号
弯路四 · 型号对比一开始比了基础频率
i5-14500（基础 2.5GHz）被判"不如" i5-10500T（2.9GHz），但它其实是 14 核的新一代。
建参数库时，字段可比性要逐个确认。同类产品的不同定位（桌面/移动、标压/低压），有些指标天然不可横向比较

六条可迁移的教训

数据契约错了，改提示词没用
任何 LLM 应用。模型输出形状 ≠ 业务需要形状时，重设计输出格式
确定性规则放代码，语义判断放模型
数值、格式、型号这类有标准的，别指望模型
"找对应关系"比"做判断"更易出错
表对表比对、记录匹配、实体对齐类需求
换模型 > 调工程
发现自己一直在给模型的错兜底时
需求要写成可验收的规格，不是口头描述
产品与开发的协作，尤其是和 AI 协作
改主流程必须跑全量验证
任何交付前的最后一道关

如果重来一次

会提前做的三件事

1. 第一天就要一份书面需求基线
成本：用户多花 1 小时写文档。收益：省掉四轮返工。

2. 第一天就搭自动验收脚本
v2.0 之后才有，但那之后没再出现统计不自洽这类低级问题。

3. 先用最强模型跑通，再考虑降本
一开始用免费模型省成本，结果大量时间花在跟模型能力不足搏斗。

会保持不变的两件事

1. 判定权分层（规则优先、模型兜底）
这是准确率的根基。

2. 输出格式严格遵守规格（序号同步原文、两档汇总、只标 A 列）
这是它"能用"而不是"看起来能用"的原因。

06 / 可复用性

这套骨架还能用在哪
