> 分享对象：产品 / 研发 / 业务团队
> 项目周期：2026-11-24 ~ 11-25（两天，11 个版本迭代）

## 0. 一页纸摘要

**做了什么**：把「招投标技术参数逐条核验」这件人工活，做成一个上传 Excel 就出结论的本地工具。

**核心价值**：28 行招标文本、244 个参数点的核验，从「人工逐条比对、几十分钟、容易看漏」，变成「上传 → 45 秒 → 带标红的核验报告」。

**关键数字**：

| 指标 | 结果 |
|---|---|
| 单次核验耗时 | 244 个参数点，浏览器端 **45 秒**（命令行 6.6 秒） |
| 判定准确率 | 关键案例逐条核对通过，5 条自动验收标准全过 |
| 模型漏判 | 0 处（换模型前是 15 处） |
| 代码规模 | 2417 行（前端 1217 + 后端 200 + 数据/工具 1000） |
| 迭代次数 | 11 个版本，两天 |

**最有价值的一条教训**：

> 当「模型输出的数据形状」和「业务需要的数据形状」不一致时，改提示词是没用的，**必须改输出契约**。
> 我在 v1.x 阶段给它打了四轮补丁，越打越歪；v2.0 重做架构后一次到位。

## 1. 项目背景

### 1.1 业务场景

设备采购的招投标环节，评标需要做一件事：

> 把招标文件里的**技术参数要求**（A 列），和投标方提交的**技术响应**（B 列），逐条比对，判断每条是否满足。

一份典型的对照表长这样：

| 招标要求（A 列） | 投标响应（B 列） | 核验结论（C 列） |
|---|---|---|
| 1、处理器：≥6核12线程，主频≥2.3GHz，睿频≥3.8GHz，TDP≤35W（性能不低于 i5-10500T） | 1、处理器：i5-14500 | **？** |
| 2、内存：≥8GB DDR4 | 2、内存：16GB DDR4 | **？** |
| 3、积木种类≥90种，积木数量≥900块 | 3、组件种类不少于40种，数量不少于323个 | **？** |

真实文件是 **28 行、244 个参数点**，每行 A 列本身又是一段含多层编号的长文本。

### 1.2 人工做法的三个痛点

**痛点一：慢且枯燥。**
244 个参数点，需要逐条读、逐条比、逐条判断。一条参数平均 30 秒，就是 2 小时；熟练的人也要 40 分钟以上。

**痛点二：容易看漏，且漏了看不出。**
最危险的不是判错，是**跳过去了没发现**。比如招标要求"支持 VoiceID 声纹识别"，投标响应里根本没提这件事 —— 人眼扫过去容易默认"大概有吧"，实际是缺项。

**痛点三：判断标准不统一。**
同一个参数，不同人判的结论可能不同：
- 要求「≥6自由度」，响应「9自由度」—— 有人判满足，有人判"不一致"
- 要求「≥8GB」，响应「16GB」—— 这是满足、正偏离、还是"响应超出要求需澄清"？
- 要求里的型号「不低于 i5-10500T」，响应「i5-14500」—— 不懂硬件的人根本判不了

### 1.3 为什么值得做

三个理由：

1. **规则明确、可自动化**。这是个"有标准答案"的判断题，不是开放式创作，适合交给模型 + 确定性规则。
2. **高频重复**。每次采购都要做，不是一次性活。
3. **错了代价高**。漏判一个负偏离，可能导致验收阶段扯皮、甚至采购损失。

## 2. 产品方案

### 2.1 一句话定义

> 上传招标/投标对照 Excel → 逐条判定每条参数的状态 → 输出带结论、明细、标红的核验报告。

### 2.2 四个核心设计决策

这四个决策是整个产品的骨架，也是和"AI 一句话批改"最本质的区别。

#### 决策一：逐条四态判定，而不是"只报问题"

**错误做法（v1.x 犯过）**：只让模型输出"有问题的条目"，满足的不管。
**为什么错**：满足项被丢弃后，"总数 - 问题数"反推出来的满足数**不可信**。
实际出过事故：模型报 `total_points=10`，却列出 28 条问题 —— 自相矛盾。

**正确做法**：模型必须对**每一条**输出状态，四选一：

| 状态 | 含义 |
|---|---|
| 匹配 | 响应满足要求（含等于阈值） |
| 正偏离 | 响应**明确优于**要求 |
| 负偏离 | 响应低于 / 不满足要求 |
| 待确认 | 投标里找不到对应内容，或表述含糊 |

**关键约束**：四个状态的数量之和，必须恒等于该行参数点总数。这条约束让所有统计天然自洽，不需要事后"修数字"。

#### 决策二：序号严格同步招标原文

原始招标文本长这样：

```
一、脑电波采集交互
1.采集方式：佩戴设备
2.实时采集信号
二、手势识别交互
1.采集方式：屏幕绘制
```

核验结论必须能**直接定位回原文**，所以序号原样输出 `【1、】`、`【二、1】`、`【（3）】`，**不重新编号**。

这条看起来是小事，实际很关键：
- 用户拿着结论回 Excel 找原文，靠的就是这个序号
- 如果我自己造一套"第1项、第2项"，用户根本对不上
- 多章节场景下，四个章节都有"1."，重编号必然混乱

#### 决策三：汇总只有两档，明细只列问题

**汇总**：`全部满足` / `部分满足`（两档，没有第三档）。

**明细**：只列负偏离和待确认，不列匹配和正偏离。

为什么？因为工具的定位是"**找出需要人处理的地方**"，不是"写一份完整报告"。
用户扫一眼 C 列，只想知道：这行有没有问题、问题在哪。

输出格式长这样：

```
部分满足｜共17项：负偏离6/待确认10/匹配0/正偏离1

负偏离：
  1、【2、】存储不低于16GB，支持SD卡。->仅4M flash/224K RAM，远低于16GB且未提SD卡
  2、【3、】主控器配备不小于4英寸触摸屏。->响应128*64LCD屏，远小于4英寸触摸屏

待确认：
  1、摄像头像素300w->投标参数中未找到对应内容，置信度0.5
```

#### 决策四：标红只标招标列（A 列）

**最初做法**：把 C 列（结论）整格标红。
**问题**：红色满屏，反而看不出重点；而且用户要看的是"招标要求里哪一条有问题"，不是"哪一行有问题"。

**最终做法**：只把 A 列中**负偏离/待确认的那几段文字**标红加粗，C 列不整格红。

技术上有个坑：Excel 一个单元格内的局部文字变色，需要写**富文本（rich text runs）**。普通导出库只支持整格样式，做不到。解决方案见 3.2。

### 2.3 交互流程

```
① 上传 Excel（自动识别 A/B 列）
   ↓
② 本地预判（毫秒级，60% 参数点在这一步就判完了，不花钱不耗时）
   ↓
③ 剩余条目送模型，按片并发
   ↓
④ 漏返回的条目补判一轮
   ↓
⑤ 结果表格 + 结论统计
   ↓
⑥ 导出 Excel（保留原格式 + 局部标红）
```

### 2.4 需求基线：这个项目最大的产品教训

v1.x 阶段，我是**根据用户的零散反馈**在迭代 —— 用户发张截图说"这里不对"，我修一下，再等下一张截图。

结果：修了 4 轮，用户评价"**质量很差**"。

转折点是用户**自己手写了一份需求文档**（拍照片给我），里面写清了：
- 每个条目独立判定，四种状态
- 统计口径：`共N项：负偏离X/待确认Y/匹配Z/正偏离W`
- 序号必须同步原文
- 汇总只有两档
- 明细只列负偏离与待确认
- 标红的是招标列

拿到这份文档后，我做的第一件事是**逐条比对现有实现，判定"结构不匹配，必须重做"**，而不是继续修。

这件事的教训：

> **产品经理的价值不在于提需求，而在于把需求写成可验收的规格。**
> 用户脑子里清楚"序号要同步原文"，但前四轮从没说过，因为觉得"这不是显然的吗"。
> 恰恰是这些"显然的细节"，决定了工具能不能用。

## 3. 实现路径

### 3.1 技术选型

| 层 | 选择 | 为什么 |
|---|---|---|
| 前端 | 单页 HTML（1217 行，无框架） | 用户是产品经理，要能自己启动、自己改。不需要构建工具 |
| 后端 | Python 标准库 HTTP 服务（200 行） | 只做两件事：托管静态文件 + 转发 LLM 请求（藏住 key） |
| 模型 | 火山引擎 Ark · DeepSeek V4.1 Flash | 见 3.4，换模型是最大的性能杠杆 |
| Excel | SheetJS（读）+ JSZip（后处理富文本） | 见 3.2 |
| 部署 | 本地运行（`启动工具.command` 双击） | 数据敏感（招投标文件），不出内网 |

**为什么不用 Vite/React**：整个工具体积小、无路由、无状态管理需求。用框架反而增加"用户改不动"的门槛。
**为什么后端只做代理**：API Key 不能放前端。200 行 Python 标准库足够，不引 FastAPI 减少依赖。

### 3.2 三个技术难点的解法

#### 难点一：单元格内局部文字标红

**问题**：SheetJS 只能读富文本、**不能写**（写进去得到空值）。Excel 的"一格内部分文字变色"需要 `<is><r><rPr>` 这样的富文本 XML。

**解法**：

```
生成 xlsx（SheetJS 正常导出）
   ↓
用 JSZip 打开这个 zip
   ↓
定位 xl/worksheets/sheet1.xml
   ↓
把目标单元格整块替换成 inlineStr 富文本：
  <c r="A15" s="4" t="inlineStr">
    <is>
      <r><rPr>...正常样式...</rPr><t>前面的文字</t></r>
      <r><rPr><color rgb="FFFF0000"/><b/></rPr><t>要标红的文字</t></r></r>
    </is>
  </c>
   ↓
重新打包下载
```

**踩的坑**：`wsCell` 读单元格文本时，部分原文件的 `c.r` 是**原始 XML 字符串**（`<t>...&#10;...`），直接当文本用会污染标红内容。必须优先取 `c.v`。

#### 难点二：给条目找对「对应的投标内容」

这是整个项目**最容易错、也最影响准确率**的地方。

场景：A 列第 3 条要求「积木种类≥90种」，B 列里哪一条是它的响应？

**试过三条路，全都有坑**：

| 方法 | 问题 |
|---|---|
| 按序号匹配（A 的"1."对 B 的"1."） | 多章节场景下 A 有 4 个"1."，B 也有 4 个，全对错了 |
| 按文本相似度 | 长词分词会放大数值差异，"≥8GB" vs "16GB" 算出相似度不足 0.5，找不到对应条目 → 数值判断根本没机会跑 |
| 按位置（第 N 条对第 N 条） | A/B 条目数经常不相等（B 可能合并或拆分），位置对不上 |

**最终解法**：**序号 + 同序号出现次序**

```
A 的第 1 个"1." → B 的第 1 个"1."
A 的第 2 个"1." → B 的第 2 个"1."
```

同时把文本相似度算法从"长词命中率"改成 **2-gram 滑窗命中率**，作为兜底。
效果：`不少于6自由度` vs `9自由度（颈部6+机身1+天线2）` 从"匹配失败"变成"正确判正偏离"。

> **这条是全场最重要的技术教训**：
> **"找对应关系"比"做判断"更容易出错。**
> 找错对象时，后面所有数值比较、文本一致性判断，全部建立在错误基础上，答案必然是错的，而且错得毫无征兆。

#### 难点三：型号参数需要外部知识

**问题**：招标要求「≥6核12线程（性能不低于 i5-10500T）」，投标响应「i5-14500」。
模型不知道这两颗 CPU 谁强，判成了"负偏离"。

**解法**：建本地型号参数库。

- `data/hw-specs.js`：101 个内置型号（Intel 8~14 代、AMD R3/R5/R7/R9、NVIDIA RTX/GTX、树莓派），字段：核数/线程/基础频率/睿频/功耗/显存/尺寸
- `data/hw-matcher.js`：文本 → 型号提取 → 展开参数 → 与要求逐项比

**三个关键设计决策（都是踩坑换来的）**：

| 决策 | 原因 |
|---|---|
| 型号之间**只比核数/线程/睿频，不比基础频率** | i5-14500 基础频率 2.5，**反而低于** i5-10500T 的 2.9，但它是 14 核。比基础频率会得出"14500 更差"的荒谬结论 |
| 招标点名"性能不低于 X 型号"时，**功耗不参与比较** | i5-14500 是 65W，会撞上招标的"TDP≤35W"被判负偏离，但它性能远超。点名对标型号时，用的是"性能档位"语义，不是散热约束 |
| 投标**没给型号时判待确认**，不判负偏离 | 不知道就是不知道，让人工去核，不能瞎判 |

**结果**：`i5-14500` 那条从「负偏离：低于 i5-10500T」变成「正偏离：核数14vs6、线程数20vs12、睿频4.9vs4.3」。

### 3.3 性能优化：三板斧

**基线**：v2.1，28 行 / 243 条目，**264 秒**。

#### 第一板斧：本地预判（264s → 141s）

不是所有参数点都需要模型判断。以下四类本地就能定：

1. 投标文本和招标要求**完全一致**（归一化后）→ 匹配
2. **单阈值**数值比对（要求≥8GB，响应16GB）→ 方向明确
3. 型号库能查到的 → 展开参数比
4. B 列里**完全找不到**相关内容 → 待确认

实测：**147 / 243 条（60%）本地就能判**，根本不送 AI。

#### 第二板斧：只送待判条目 + 并发（141s → 稳定）

- 不再整行整批发，只把判不出的条目按片（8 条一片）并发发
- 并发池可调（界面「并发请求数」），实测 8 最快
- **补漏机制**：模型偶发漏返回条目，把仍是 pending 的**按行聚合**再试一轮

> 为什么补漏要"按行"不能"按单条"：只发一条要求时，模型缺少上下文，容易宽松判成匹配。

#### 第三板斧：换模型（141s → 6.6s）

这是**最大的一刀**，也是我最后悔没早做的一刀。

| 指标 | 智谱 GLM-4-Flash | 火山 DeepSeek V4.1 |
|---|---|---|
| 全量耗时 | 141s（优化后） | **6.6s** |
| 模型漏返回 | 15 处 | **0 处** |
| 多阈值条目 | 判错（积木≥90种判成匹配） | **判对**（负偏离，理由带具体数字） |

**耗时降到 1/20，准确率还提升了。**

还有个细节：DeepSeek 默认开**思考模式**，每次多花 2 秒推理。逐条比对这种任务不需要推理链，关掉后单次调用 3.2s → 1.3s，判定质量完全一样。

> **教训**：我在 v2.1→v2.2 花了大功夫做工程优化（本地预判、并发、补漏），把 264s 压到 141s。
> 但换模型一步就把 141s 压到 6.6s。
> **当你发现自己在反复给模型的能力不足打补丁时，先问问是不是选错了模型。**

### 3.4 工程配套：让 AI 能自证

这个项目有个特殊约束：**我没有图形界面可以点**，每次验证都要重启服务 + 开浏览器 + 等几分钟，还被环境反复打断。

所以我做了套命令行工具链，**不依赖浏览器就能跑完整链路**：

| 工具 | 作用 |
|---|---|
| `tools/xlsx转json.py` | 源表 → JSON（含脏数据过滤） |
| `tools/回归验证.js` | 命令行跑完整判定链路，**5 分钟**跑完 28 行 |
| `tools/生成结果Excel.py` | JSON → 带格式和标红的 xlsx |
| `tools/验收检查.py` | **5 条验收标准自动核对** |

**验收脚本是关键**。它把"需求文档"变成了可执行断言：

| 验收项 | 断言 |
|---|---|
| 验收1 | 统计数字自洽（四数之和 == 条目总数） |
| 验收2 | 统计数字 == 明细行数 |
| 验收3 | 序号严格同步招标原文 |
| 验收4 | A 列标红行数 == C 列"部分满足"行数 |
| 验收5 | "全部满足"行不出现明细 |

每次改完代码跑一遍，**不靠肉眼判断"应该没问题"**。

## 4. 产出结果

### 4.1 量化指标

| 维度 | 数据 |
|---|---|
| 处理规模 | 28 行招标文本 / 244 个参数点 |
| 耗时 | 浏览器端 **45 秒**（并发 8）<br>命令行 **6.6 秒** |
| 失败行 | 0 |
| 模型漏返回 | 0 处 |
| 统计自洽 | 100%（244 = 匹配+正偏离+负偏离+待确认） |
| 验收标准 | 5 条自动断言全部通过 |
| 标红准确 | 9 处标红 == 9 行部分满足，完全一致 |

### 4.2 准确率验证（关键案例）

不是"跑通了"，是逐条核对过对错：

| 案例 | 招标要求 | 投标响应 | 正确结论 | 工具结论 |
|---|---|---|---|---|
| 数值超标 | 内存≥8GB | 16GB | 正偏离 | ✅ 正偏离（16优于8） |
| 数值不足 | 积木≥90种/≥900块 | 40种/323块 | 负偏离 | ✅ 负偏离（带具体数字） |
| 型号对比 | 不低于 i5-10500T | i5-14500 | 正偏离 | ✅ 正偏离（核数14vs6） |
| 单位不可比 | 使用时间≥110min | 电池续航16小时 | 待确认 | ✅ 不硬比（单位不同） |
| 缺项 | 支持 VoiceID 声纹 | 未提及 | 待确认 | ✅ 待确认（未找到对应） |
| 原文照抄 | 支持人脸识别 | 支持人脸识别 | 匹配 | ✅ 匹配 |

> 最后两行是最容易被模型判错的：模型倾向于把"找不到对应内容"判成"负偏离"。
> 需求文档明确写了这种情况是**待确认**，所以我在前端加了硬规则：
> 负偏离的理由里如果出现"未提及/未提供/未找到"，自动改判待确认。
> **但**如果理由同时有"不足/低于/未达到"（明确不满足），保持负偏离。

## 5. 项目复盘

### 5.1 做对了什么

**1. 判定权分层：规则优先，模型兜底。**
不确定的规则（数值大小、型号性能、文本完全一致）全部放前端代码，只有"需要语义理解"的才交给模型。
结果是模型即使判错，也会被本地规则纠正。这也解释了为什么换模型前后关键案例都判得对。

**2. 加了自动验收，不靠肉眼。**
5 条断言覆盖了最容易出错的统计一致性和格式同步。每次改完就跑，省掉了大量"看起来对"的误判。

**3. 需求文档化后才动手。**
虽然是被用户"骂"出来的，但拿到手写需求后重做的效率，远高于之前四轮散点修补。

**4. 把踩坑原因写进代码注释和 CHANGELOG。**
比如「这里要用 pre 不能用 rows」「型号对比不比基础频率」。
**原因**：这个项目大量依赖 AI 辅助编码，而 AI 每次对话都是"失忆"的。不写下来，下次同样会犯。

### 5.2 走过的弯路（重点讲这个）

#### 弯路一：给模型的错误打补丁，越打越歪（v1.0 → v1.4）

**现象**：用户反馈"这条判错了" → 我加条规则 → 下次另一条又错 → 再加规则。
四轮下来：
- v1.1 修数值方向
- v1.2 修二级序号
- v1.3 修局部高亮
- v1.4 修正偏离误报 + 高亮缺失

**根本问题**：不是某条规则不对，是**数据契约错了**。
v1.x 让模型"只报有问题的条目"，满足项被丢掉，前端靠 `总数 - 问题数` 反推满足数。这个设计从第一天就不可能自洽。

**转折**：用户说"质量很差"，手写需求文档。我逐条比对后判定"结构不匹配，必须重做"，v2.0 把输出契约改成"每条都必须给状态"。

**教训**：
> 连续三轮以上都在修同类问题时，停下来问一句：**是不是模型和数据之间的契约错了？**
> 打补丁的边际收益会越来越低，因为你在跟一个结构性问题搏斗。

#### 弯路二：只跑单行就宣布"修好了"（v2.4 翻车）

**现象**：v2.2 加进度提示时写了 `rows.reduce((s,r) => s + r.items.filter(...))`。`rows` 是原始行，没有 `items` 字段。用户一点核验就崩。

**为什么没发现**：这行在 `if (jobs.length)` 里面，只有"存在需要送 AI 的条目"才执行。我测试时跑的样本本地就判完了，`jobs` 是空的，走不到这行。

**教训**：
> **改动主流程后必须跑全量。** 单行测试通过 ≠ 功能正常，尤其是条件分支里的代码。
> 另外：异步主流程应该默认包 `try/finally` 复位 UI 状态。这次出错后按钮永久锁死，只能刷新页面 —— 二次伤害。

#### 弯路三：把工程优化当成了主要矛盾（v2.2）

**现象**：花了不少功夫做本地预判、并发池、补漏机制，264s → 141s，觉得挺满意。

**真相**：换个模型 141s → 6.6s，而且准确率还提升了（漏返回 15 → 0）。

**教训**：
> 优化之前先量一下瓶颈在哪。**这次瓶颈根本不在我的代码里，在模型。**
> 当你发现自己不断给模型的失误做兜底逻辑（补漏、纠正、二次校验），这本身就是"该换模型"的信号。

#### 弯路四：型号对比一开始比了基础频率

**现象**：i5-14500（基础 2.5GHz）被判"不如" i5-10500T（2.9GHz），但它其实是 14 核的新一代。

**教训**：
> 建参数库时，**字段可比性要逐个确认**，不能想当然地把所有数字都拿来比。
> 同类产品的不同定位（桌面/移动、标压/低压），有些指标天然不可横向比较。

### 5.3 六条可迁移的教训

如果只记六条，记这些：

| # | 教训 | 适用场景 |
|---|---|---|
| 1 | **数据契约错了，改提示词没用** | 任何 LLM 应用。模型输出形状 ≠ 业务需要形状时，重设计输出格式 |
| 2 | **确定性规则放代码，语义判断放模型** | 数值、格式、型号这类有标准的，别指望模型 |
| 3 | **"找对应关系"比"做判断"更易出错** | 表对表比对、记录匹配、实体对齐类需求 |
| 4 | **换模型 > 调工程** | 发现自己一直在给模型的错兜底时 |
| 5 | **需求要写成可验收的规格，不是口头描述** | 产品与开发的协作，尤其是和 AI 协作 |
| 6 | **改主流程必须跑全量验证** | 任何交付前的最后一道关 |

### 5.4 如果重来一次

**会提前做的三件事**：

1. **第一天就要求一份书面需求基线**，而不是靠截图反馈迭代。
   成本：用户多花 1 小时写文档。收益：省掉四轮返工。

2. **第一天就搭自动验收脚本**。
   v2.0 之后才有验收脚本，但那之后没再出现"统计不自洽"这类低级问题。

3. **先用最强的模型跑通，再考虑降本**。
   一开始用免费模型省成本，结果是大量时间花在跟模型能力不足搏斗。后来换 DeepSeek，成本没增加多少，速度快 20 倍、准确率还更高。

**会保持不变的两件事**：

1. **判定权分层**（规则优先、模型兜底）—— 这是这个工具准确率的根基。
2. **输出格式严格遵守用户规格**（序号同步原文、两档汇总、只标 A 列）—— 这是它"能用"而不是"看起来能用"的原因。

## 6. 可复用性：这套方法还能用在哪

这个项目的骨架其实是通用的：**「两份文本逐条比对 + 四态判定 + 带定位的输出」**。

可以直接迁移的场景：

| 场景 | 相似度 | 需要改什么 |
|---|---|---|
| 合同条款比对（甲方/乙方版本） | 高 | 状态定义改为 一致/偏向甲方/偏向乙方/缺失 |
| 需求文档 vs 开发交付物验收 | 高 | 状态改为 已实现/超出/未实现/待确认 |
| 竞品功能对比表 | 中 | 改为横向多列比对 |
| 供应商资质审核 | 中 | 加入证照有效期等规则校验 |
| 教学大纲 vs 教材内容覆盖度 | 中 | 状态改为 已覆盖/部分覆盖/未覆盖 |

**可复用的三个组件**：

1. **分层判定框架**：本地确定性规则 + 模型语义判断 + 冲突时规则优先
2. **序号同步机制**：保留原文编号，保证结论可定位回原文
3. **验收断言脚本**：把需求规格变成可执行断言
