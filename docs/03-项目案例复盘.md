# 招投标参数核验工具 · 项目复盘

> 视角：产品经理 + 交付经理
> 周期：2026-11-24 ~ 11-25（两天，11 个版本迭代）
> 我的角色：产品定义、需求规格化、交付验证

---

## 一、项目背景：为什么做这件事

### 1.1 这是一个什么业务动作

设备或服务采购的招投标环节，评标要做一件很机械但很关键的事：

> 把招标文件里的**技术参数要求**，和投标方提交的**技术响应**，逐条比对，判断每条是满足、不满足、还是说不清。

这不是开放式分析，而是一道**有标准答案的判断题**。招标要求写"内存≥8GB"，响应写"16GB"，答案就是"优于要求"。这类任务的共同特征是：规则明确、高频重复、判错代价高——天然适合产品化。

### 1.2 人工做，成本 High 在哪

我以评委/采购经办人的视角算了三笔账：

**第一笔：时间账。**
一份中等规模的对照表，参数点通常在**几十到上百条**。逐条读、逐条找对应、逐条判断，一条按 30 秒算，就是**半小时到两小时**的纯重复劳动。而且每次采购都要重来一遍，不是一次性活。

**第二笔：质量账。**
最危险的不是"判错"，是"**漏了没发现**"。招标要求里提到某项能力（比如某个认证、某个接口），投标响应通篇没提——人眼扫过去容易默认"应该有吧"，实际是缺项。这种漏判在验收阶段才会暴露，到时候已经晚了。

**第三笔：一致性账。**
同一个参数，不同人判的结论可能不同：
- 要求"≥8GB"、响应"16GB"——有人判"满足"，有人判"响应超出，需澄清"
- 要求"性能不低于某型号"、响应"另一型号"——不懂硬件的人根本判不了
- 要求"≥6自由度"、响应"9自由度"——有人判满足，有人判"表述不一致"

标准不统一，导致核验结果不可复核、不可交接。

### 1.3 为什么值得做

三个理由，缺一不可：

1. **规则可枚举**：判定逻辑能用规则 + 语义判断组合表达，不是黑箱审美题
2. **高频复用**：每次采购都做，做一次工具能反复用
3. **错误成本高**：漏判一个负偏离，可能导致验收扯皮甚至采购损失

这三点决定了它不是"做个 demo 玩玩"，而是有真实交付价值的产品。

## 二、产品方案：从痛点到设计

### 2.1 一句话定义

> 上传招标/投标对照 Excel → 逐条判定每条参数的状态 → 输出带结论、可定位原文、带标红的核验报告。

产品的定位不是"写一份漂亮的报告"，而是"**把需要人处理的地方挑出来**"。这个定位决定了后面所有取舍。

### 2.2 核心设计：六个痛点 → 六个决策

这是整个方案的主干。每一条设计决策，都能追溯到一个具体用户痛点。

| # | 用户痛点 | 设计决策 | 为什么这样解 |
|---|---|---|---|
| 1 | 逐条比对慢、量大 | **判定权分层**：确定性规则本地判，只有语义歧义才送模型 | 让机器做机器擅长的，把昂贵的 AI 调用留给真正需要理解力的地方 |
| 2 | 漏判看不出 | **四态判定**：每条必须输出状态，缺项显式归入"待确认" | "找不到对应内容"必须被暴露成一个明确结果，不能被默认为"满足" |
| 3 | 统计对不上、不可复核 | **输出契约固定**：四态数量之和恒等于条目总数 | 结构约束让统计天然自洽，而不是事后去修数字 |
| 4 | 结论对不上原文 | **序号严格同步原文**，不重新编号 | 用户拿着结论要回 Excel 找原文，靠的就是原始序号 |
| 5 | 满屏结论看不出重点 | **汇总两档 + 明细只列问题 + 标红只标招标列** | 用户只想知道"这行有没有问题、问题在哪"，不是读完整报告 |
| 6 | 型号参数不懂 | **内置领域参数库**，型号对标由库裁决 | 把"领域知识"沉淀成产品能力，而不是依赖模型临时发挥 |

**这六条里，产品判断最重的是第 2 条和第 5 条：**

- 第 2 条把"不确定性"设计成一等公民。市面上很多同类工具会把"没找到"当成"满足"糊弄过去，那是拿用户的验收风险换一张好看的报告。我选择让它显式暴露。
- 第 5 条是典型的**克制**：功能上完全可以输出全部条目的详细理由，但那会让真正的问题淹没在信息里。产品价值不在于"给得多"，在于"让用户一眼看到该看的"。

### 2.3 产品结构

四层结构，职责边界清晰：

```
输入层    Excel 上传 → 识别 A 列（要求）/ B 列（响应）
   ↓
理解层    条目拆分（含多层编号）→ 结构识别（过滤分组标题）
   ↓
判定层    本地规则（数值/文本/型号库）→ 语义歧义送模型 → 异议复核
   ↓
输出层    四态结论 → 统计汇总 → 原文定位 → 标红导出
```

**分层带来的最大好处**：任何一层出问题，可以单独定位、单独替换。比如模型不行就换模型，不影响拆分和导出；拆分规则要改，也不用动判定逻辑。

### 2.4 交互流程

```
① 上传 Excel
② 本地预判（多数参数点在这一步判完，不花钱不耗时）
③ 剩余条目送模型，按片并发
④ 漏返回的条目补判一轮
⑤ 结果表格 + 统计
⑥ 导出 Excel（保留原格式 + 局部标红）
```

## 三、落地结果：数据 + 典型场景

### 3.1 效果数据

在一份**中等规模真实样本**（数十行、上百个参数点）上的实测：

| 维度 | 人工基线 | 工具结果 |
|---|---|---|
| 单次耗时 | 半小时 ~ 两小时 | 浏览器端**几十秒**，命令行**秒级** |
| 漏判 | 依赖人眼，难发现 | 缺项显式归入待确认，**0 漏判** |
| 统计自洽 | 人工汇总易错 | **100%**（四态之和恒等于条目总数） |
| 判定一致性 | 因人而异 | 规则 + 契约约束，**同一输入同一输出** |
| 验收断言 | 无 | **5 条自动断言全部通过** |

**最关键的两个数字**：
- 耗时从人工的"半小时级"压到"几十秒级"——把人从重复劳动里解放出来
- 模型漏返回从 15 处降到 0 处——这是换模型带来的，不是改代码带来的（见复盘第 3 点）

### 3.2 典型场景分析

不看具体某份文件，看**五类高频场景**——这才是可复用的部分：

| 场景类型 | 典型表现 | 工具结论 | 判断依据 |
|---|---|---|---|
| **数值优于要求** | 要求 ≥X，响应 >X | 正偏离 | 数值方向裁决 |
| **数值低于要求** | 要求 ≥X，响应 <X | 负偏离 | 带具体数字说明差多少 |
| **单位不可比** | 要求 min，响应"小时" | 待确认 | 单位不一致，不硬比，交人工判断 |
| **型号性能对标** | 要求"不低于 A 型号"，响应 B 型号 | 由参数库裁决 | 比核数/线程/睿频，不比基础频率，功耗不参与 |
| **缺项 / 分组标题** | 要求有、响应通篇未提；或"硬件参数"这类大标题 | 待确认 / 过滤 | 不把标题当条目，不把缺项当满足 |

**两个值得单独说的案例：**

**案例 A：型号对标反直觉。**
点名"性能不低于 A 型号"时，B 型号的基础频率反而更低，但它是更新代、核心数翻倍。如果按"数字大的更好"的朴素逻辑会判成负偏离——这是错的。产品上我把"型号对标"单独定义成一个场景，明确"比代际和核心规格、不比单一频率、功耗不参与"，并把领域参数库作为产品能力内置。这类判断靠提示词说不清楚，必须靠产品规则 + 数据。

**案例 B：单位不可比时的"克制"。**
要求"续航≥110min"，响应"16小时"。数字上 16 < 110 看似负偏离，但单位不同根本不能比。工具判"待确认"并说明原因，而不是硬给一个结论。**一个诚实的不确定性，比一个看起来确定的错误答案更有价值。**

### 3.3 交付形态

- 工具本体：单页 HTML + 本地代理，双击启动，无需安装依赖
- 交付验证：命令行工具链，不依赖浏览器就能跑完整链路 + 自动验收
- 公网版本：部署到云服务器，支持访问口令鉴权 + 开机自启，客户可外网访问

## 四、过程复盘：产品与交付视角

不按"我写了什么代码"流水账，按**五个关键决策点**讲——每个都回答：遇到什么、怎么想、怎么解、沉淀了什么。

### 决策点 1：需求基线事件 —— 产品的第一课

**遇到什么**：v1.x 阶段，我根据用户零散反馈迭代——用户发截图说"这里不对"，我修一下，再等下一张。修了四轮，评价是"质量很差"。

**怎么想**：我一开始以为是"修得不够细"。后来意识到，问题是**需求从来没有被规格化过**。用户脑子里清楚"序号要同步原文""汇总只有两档"，但觉得"这不是显然的吗"，从没说过。这些"显然的细节"恰恰决定了工具能不能用。

**怎么解**：用户手写了一份需求文档后，我没有继续打补丁，而是**逐条比对现有实现，判定"结构不匹配，必须重做"**，v2.0 整体重构。

**沉淀**：
> 产品经理的价值不在于"接需求"，而在于把需求写成**可验收的规格**。
> 用户说不清的"显然"，正是产品要追问出来的东西。

### 决策点 2：数据契约重做 —— 结构性问题的识别

**遇到什么**：模型输出"只有问题的条目"，满足项被丢弃，前端靠"总数 - 问题数"反推满足数。结果出现过"总数报 10 项、却列出 28 条问题"的自相矛盾。

**怎么想**：连续几轮都在修同类错误，边际收益越来越低。这不是某条规则不对，是**模型输出的数据形状和业务需要的数据形状不一致**——是契约错了。

**怎么解**：把输出契约改成"每条都必须给状态"，四态之和恒等于总数。结构对了，统计自然自洽。

**沉淀**：
> 连续三轮以上都在修同类问题时，停下来问：**是不是底层契约错了？**
> 给错误打补丁，越打越歪；改契约，一步到位。

### 决策点 3：性能瓶颈定位 —— 交付的判断力

**遇到什么**：全量核验要 264 秒，太慢。

**怎么想**：作为交付负责人，先问"瓶颈在哪"，而不是直接开干。我先做了工程优化（本地预判、并发、补漏），264s → 141s。然后发现——**瓶颈根本不在代码里，在模型**。

**怎么解**：换模型后 141s → 秒级，且准确率反而提升（漏返回 15 → 0）。关掉模型默认的思考模式，又省一半时间。

**沉淀**：
> 当你发现自己一直在给模型的失误做兜底逻辑（补漏、纠正、二次校验），这本身就是"**该换模型**"的信号。
> 优化之前先量瓶颈，别在错误的地方使劲。

### 决策点 4：交付验证机制 —— 从"能跑"到"可信"

**遇到什么**：改完主流程后，一次用户点击就崩。原因是 bug 藏在一个条件分支里，我测试用的样本本地就判完了，根本走不到那行。

**怎么想**："我测过没问题"和"真的没问题"是两回事。单点测试覆盖不到条件分支，尤其在异步主流程里。

**怎么解**：建了命令行回归工具链 + **5 条自动验收断言**（统计自洽、序号同步、标红对应等）。每次改完跑全量，不靠肉眼。

**沉淀**：
> 交付物必须**可验证**。把需求规格变成可执行断言，比"看起来对"可靠得多。
> 改主流程必须跑全量——这是交付前的最后一道关。

### 决策点 5：公网交付 —— 交付经理的最后一公里

**遇到什么**：工具本地跑通后，客户要外网访问。 GitHub Pages 只能放静态文件，跑不了后端、藏不住 key——页面能打开，但一点核验就降级成演示模式。

**怎么想**：这是典型的"**本地能跑 ≠ 交付完成**"。客户场景里的约束（网络、系统、安全）必须在交付方案里被解决，不能留给用户。

**怎么解**：部署到云服务器；遇到服务器是 Windows Server、下载源慢、无鉴权裸奔等问题，逐一解决——换国内镜像源、加访问口令、注册开机自启。最终做到：客户拿一个链接就能用，服务器重启自动恢复，陌生人拿到链接也烧不了 key。

**沉淀**：
> 交付的边界是"客户能用"，不是"我能跑"。
> 部署环节的每个约束都要当成产品问题来解决，而不是甩给用户。

### 4.6 可迁移的方法论

如果这份复盘只留五条，留这些：

| # | 方法论 | 适用场景 |
|---|---|---|
| 1 | 需求要写成**可验收规格**，不是口头描述 | 任何产品与开发的协作 |
| 2 | 数据契约错了，改提示词没用 | 所有 LLM 应用 |
| 3 | 把"不确定性"设计成一等公民，不假装确定 | 判定类、审核类产品 |
| 4 | 优化前先量瓶颈，别给错误的东西打补丁 | 性能与成本优化 |
| 5 | 交付边界是"客户能用"，本地能跑不算完 | 所有对外交付 |
